# Deployment

[Wiki home](../README.md)

The repository has three independently deployed surfaces: Convex, the Next.js
application, and Google Apps Script. Deploying one does not deploy the others.

## Known and unknown facts

Known from repository configuration:

- Next.js can build and run as a Node production application.
- Convex functions and schema are deployed with the Convex CLI.
- Apps Script is connected and pushed with `clasp`.
- CI checks ranking-runtime synchronization only.

Known from the connected GitHub repository and confirmed workflow:

- Git pushes are connected to Vercel.
- A non-production `preview/*` branch push triggers a Vercel preview deployment.
- Vercel reports deployment state and its direct URL through GitHub's
  Deployments API.

Not encoded in this repository:

- the Vercel project/team identifier
- production domains
- Vercel project settings and environment values
- a deployment approval process
- a tested web or Convex rollback procedure
- automatic Apps Script trigger provisioning

There is no checked-in `vercel.json`, `.vercel/project.json`, or web deployment
workflow. Treat GitHub as the trigger and the GitHub deployment status as the
source for the exact preview URL; do not infer project settings or production
domains from generated URLs.

## Pre-deployment checks

1. Inspect `git status` and the exact diff; preserve unrelated user changes.
2. Identify which of the three runtimes changed.
3. Run the targeted checks in [Verification](verification.md).
4. Confirm environment-variable names and values in the owning secret store
   without printing values.
5. Confirm the target deployment, project, or clasp identity.
6. Review schema migrations and every possible data mutation.
7. For shared ranking code, synchronize before deploying either runtime.

## Convex deployment

During local backend development:

```bash
npx convex dev
```

This pushes to and watches the configured development deployment. For local
binding generation without changing a deployment, use `npx convex codegen`.

Deploy functions and schema from the repository root:

```bash
npx convex deploy
```

Protected functions require matching environment configuration in the target
deployment. For example:

```bash
npx convex env set CONVEX_SERVER_SECRET <value>
```

Never place the value in documentation or shell history that will be shared.
Other Convex authentication and worker names are listed in
[Environment](../reference/environment.md).

`convex.json` contains only the schema reference and does not identify the
production deployment. Verify the Convex CLI target before deploying.

The generated bindings under `convex/_generated/` are regenerated by Convex
development tooling. Do not hand-edit them. When a local operator command says
that maintenance functions are unavailable, deploy the current Convex
functions before retrying the command; do not work around the preflight.

Convex code-defined schedules become active with the deployed backend. Review
`convex/crons.ts`, managed schedule rows, and apply-enabled automation before a
production deploy.

## Next.js application deployment

### Preview pull requests

Use the [`gshl-preview-pr`](../../.agents/skills/gshl-preview-pr/SKILL.md)
repository skill when the user asks to publish a completed goal. It isolates
only the current agent's changes on a
`preview/<goal-slug>` branch, pushes that branch, waits for the Vercel deployment
attached to the exact HEAD SHA, and creates a PR containing the returned
`environment_url` or `target_url`.

Do not guess Vercel's generated branch URL or run `vercel deploy` as a fallback.
If the GitHub deployment fails or does not report a URL, diagnose the connected
integration and stop before claiming a usable preview. The skill does not merge
the PR or promote the preview to production.

### Local build and production handoff

The local production build gate is:

```bash
npm run build
```

Local production execution is:

```bash
npm run start
```

or:

```bash
npm run preview
```

These commands do not publish the application. Git branch publication is a
separate, explicitly authorized push through the connected GitHub/Vercel
integration.

The connected Vercel project must provide the environment needed by the enabled
features, including the public Convex URL and relevant server-only
authentication, Convex, and upload secrets. Google OAuth must include the
production callback for `/api/auth/callback/google` on the actual host domain.

The Next configuration constrains output tracing to this application and
permits configured remote image hosts. A successful local build does not prove
the externally configured Vercel environment has equivalent variables or
network access.

For a preview, report the exact URL returned for the pushed commit. Production
domains, promotion, and rollback remain externally managed and require a
separate handoff.

## Apps Script deployment

From `apps-script/`, confirm authentication and the connected project:

```bash
npm run login
npm run open
```

Push source:

```bash
npm run push
```

`npm run deploy` is only a push plus a success message. It does not create a
versioned deployment or configure production triggers.

Before pushing shared rating or power files, run from the repository root:

```bash
npm run ranking-engine:sync
npm run ranking-engine:check
```

After pushing, inspect Apps Script logs and manually validate the intended
public trigger. See [Apps Script operations](apps-script.md).

## Recommended cross-runtime sequence

When a release spans multiple runtimes, a safe sequence is:

1. back up affected production data when schema or writer behavior changes
2. deploy Convex functions/schema and verify protected endpoints
3. complete the externally configured Vercel deployment and verify sign-in and
   data reads
4. synchronize, check, and push Apps Script only if its runtime changed
5. inspect managed jobs and Apps Script schedules for unintended apply-enabled
   automation
6. run narrow smoke checks without broad data rewrites

This is a safety recommendation, not an encoded automated release pipeline.

## CI does not deploy

The only GitHub Actions workflow runs `npm run ranking-engine:check` on its
configured paths. Those filters currently omit both `PowerRankingsAlgo.js`
paths, so a power-only change does not trigger it. It does not install or deploy
the application, run Convex deployment, push Apps Script, lint, type-check,
build, or test.

## Recovery and rollback

- Preserve a Convex export before destructive data operations.
- Player-day source deletion creates a dedicated Convex ZIP snapshot; see
  [Player-day archive](player-day-archive.md).
- Keep the last known-good Apps Script source revision and confirm the connected
  project before a corrective push.
- The repository does not define a checked-in Vercel rollback procedure.
  Escalate to the Vercel project owner rather than inventing a command.
- Do not use destructive Git commands to simulate deployment rollback in a
  dirty worktree.
